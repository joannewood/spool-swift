# Spool (native macOS rewrite)

Spool is a native, single-process macOS rewrite of a Python/FastAPI/Postgres/Docker 3D-printing
file library app (source at `~/Documents/data-platform`). It watches folders you grant, hashes
and thumbnails every recognized model file (STL/3MF/STEP/STP/OBJ/SVG/gcode/SCAD), and keeps a
searchable, live-updating library — no Docker, no Postgres, no separate daemon.

**Read the original app's own `~/Documents/data-platform/CLAUDE.md` before touching ingestion,
mesh-safety, relationship-suggestion, or rescan logic.** It's a 3000+ line build log of real
production incidents (OOM crash loops from pathological 3MF files, iCloud-eviction stat hangs,
bind-mount move/duplicate-event unreliability) and the fixes they drove. Several things in this
Swift port that look like they could be simplified are deliberately not simplified further —
that file is *why*.

## Repository layout

```
spool-swift/
  project.yml              ← XcodeGen source of truth — see "Xcode project" below
  Packages/
    SpoolCore/              persistence (GRDB/SQLite), job queue, ingestion, metadata
                            extraction, relationship/project suggestion, search. No UI imports.
    SpoolMesh/              STL/OBJ/3MF/STEP parsing → shared TriangleMesh, mesh analysis,
                            SceneKit thumbnail rendering.
    SpoolFS/                FSEvents watcher, security-scoped bookmarks, archive reading.
  SpoolApp/
    App/                    App entry point, AppEnvironment (DI root), FS/root-access services.
    Views/                  SwiftUI views + their view models (one file per feature area).
    Resources/              Assets.xcassets, entitlements, Spool.help (Help Book), Info.plist.
  Tools/StepConverter/      Standalone OCCT-based CLI (STEP → mesh), invoked from the slow job lane.
```

Each package is a plain SwiftPM package with no UI dependency — `swift test` inside
`Packages/<Name>` runs its suite directly and is the fast inner loop. `SpoolApp` itself is an
Xcode application target and can't be built with `swift build`; use `xcodebuild` (below).

## Xcode project: XcodeGen is the source of truth

**`Spool.xcodeproj/project.pbxproj` is a generated artifact.** Do not treat manual edits to it
as durable — anyone (or any future session) running `xcodegen generate` will regenerate it
straight from `project.yml` and silently drop anything only added by hand to the `.pbxproj`.

- Adding a new `.swift` file under `SpoolApp/App/` or `SpoolApp/Views/` needs **no project
  changes at all** — both are folder-based `sources:` entries in `project.yml`, so XcodeGen
  auto-discovers new files there on the next `xcodegen generate`.
- Adding a new **resource** (like the `Spool.help` Help Book folder), a new **build phase**
  (like `Spool.help`'s post-build `hiutil` indexing script), or a new **Info.plist/build
  setting** must go into `project.yml`, not just the `.pbxproj` — otherwise it survives only
  until someone regenerates.
- Workflow for any of the above: edit `project.yml`, run `xcodegen generate` from the repo
  root, then verify with the `xcodebuild` command below. Don't hand-edit `.pbxproj` sections
  that `project.yml` already governs (sources, resources, script phases, build settings) —
  only fall back to raw `.pbxproj` editing for things XcodeGen has no `project.yml` surface for
  at all, and if you do, add a matching TODO here.
- There is a stray, unrelated **`Spool 2.xcodeproj`** at the repo root (not referenced by
  anything, not generated by the current `project.yml`). Ignore it; it's not the active project.

### Build & test commands

```bash
# Fast inner loop — one package at a time, no Xcode needed:
cd Packages/SpoolCore && swift test          # or SpoolMesh / SpoolFS
swift test --filter SomeSuiteName            # a single suite while iterating

# Full app build (the only way to catch SpoolApp-target-only errors,
# e.g. anything in Views/ or the Xcode-project-level Resources/build phases):
xcodebuild -project "Spool.xcodeproj" -scheme "Spool" -configuration Debug build

# After editing project.yml:
xcodegen generate
xcodebuild -project "Spool.xcodeproj" -scheme "Spool" -configuration Debug build
```

Established cadence for larger multi-file changes: run only the targeted `swift test` filter
per change while iterating; save one full per-package `swift test` (no `--filter`) and one full
`xcodebuild` for the very end of a batch, not after every single edit.

## Known gotchas (each cost real debugging time this session)

- **GRDB `Column(...)` wants the snake_case DB column name, not the Swift camelCase property
  name.** `Column("watchedRootId")` silently fails at the SQL level (`no such column`);
  it must be `Column("watched_root_id")`. `databaseColumnDecodingStrategy`/
  `...EncodingStrategy` only affect Codable row decoding, not `Column(...)`/raw SQL identifiers.
- **`/var` (and `/tmp`, `/etc`) are a macOS special case for symlink resolution.**
  `FileManager.default.temporaryDirectory` returns a `/var/folders/...` path;
  `FileManager.enumerator` returns the canonicalized `/private/var/folders/...` form for the
  same files. Foundation's `URL.resolvingSymlinksInPath()` deliberately leaves `/var`/`/tmp`/
  `/etc` unresolved (legacy compatibility), so it does **not** fix this — tests that construct
  paths under a temp dir and later compare against enumerator-discovered paths need the raw
  POSIX `realpath()` call instead (see any `makeTempDir()` helper in `SpoolCoreTests`).
- **`INFOPLIST_KEY_<Key>` build settings only work for a fixed list of keys Xcode's
  auto-generation recognizes** — arbitrary/uncommon `CFBundle*` keys (e.g.
  `CFBundleHelpBookFolder`/`CFBundleHelpBookName`) are silently dropped with no warning, even
  though `GENERATE_INFOPLIST_FILE = YES` accepts the setting name without complaint. Fix: a
  small supplemental `Info.plist` (currently `SpoolApp/Resources/Info.plist`, just the keys
  `INFOPLIST_KEY_*` doesn't cover) referenced via the `INFOPLIST_FILE` build setting alongside
  `GENERATE_INFOPLIST_FILE = YES` — Xcode merges the two.
- **`Spool.xcodeproj`/`Spool 2.xcodeproj` are gitignored, not just generated.** The repo
  (github.com/joannewood/spool-swift) tracks `project.yml` as the only source of truth for
  the Xcode project — clone, then run `xcodegen generate` before opening in Xcode. `Spool
  2.xcodeproj` is the same stray, unreferenced artifact mentioned above; excluded rather
  than deleted since it's untracked either way.
- **App Sandbox does not let a sandboxed app execute an arbitrary external binary via
  `Process`/`NSTask`, even one it has genuine file access to.** Spool used to let you grant
  a folder containing `unar`/`7z` (via a security-scoped bookmark, same mechanism as watched
  roots) so it could shell out to inspect/extract `.7z`/`.rar` archives. Confirmed live,
  methodically, that this cannot work: (1) every Homebrew `/opt/homebrew/bin/*` entry is a
  symlink into `Cellar`, and granting `bin` itself doesn't extend through the symlink to
  wherever it really points — fixable by detecting this and re-prompting for the resolved
  real directory (Settings used to do this); but even after that fix, (2) `Process.run()`
  on the *real*, directly-selected, non-symlink binary **still** fails ("the file doesn't
  exist" — sandbox's disguised permission-denied), with an active
  `startAccessingSecurityScopedResource()` on both the containing folder and the file
  itself. `FileManager.isReadableFile`/`fileExists` succeed the whole time; only
  process-execution is blocked. There is no known entitlement in this app's
  non-App-Store-but-still-sandboxed configuration that unlocks this — `StepConverterLocator`
  (`Packages/SpoolCore/Sources/SpoolCore/Jobs/`) works only because `step-tessellate` is
  bundled *inside* Spool's own signed app bundle, which sidesteps the restriction entirely
  (same-signature bundled helpers aren't "arbitrary external binaries"). Current behavior:
  `.7z`/`.rar` are always tracked as `unsupported_format` unconditionally (no tool-detection
  at all — see `ArchiveInspectionService`), and the Review window just tells the user to
  extract manually; `RescanService`'s missing-zip sweep deletes the row once the original
  archive is gone from disk. If external-tool support is ever revisited, it needs either a
  real answer to the entitlement question above or a bundled-helper redesign (like
  StepConverter) — not another bookmark/symlink workaround, that avenue is exhausted.

## Testing conventions

- **Swift Testing (`@Suite`/`@Test`/`#expect`/`#require`), not XCTest**, throughout.
- Parity-audit methodology established across this project: for any behavior with a Python
  equivalent, read the *original Python source* (not just its test file) for ground truth,
  port test-by-test (not just "behavior looks similar"), and verify via actually running
  `swift build`/`swift test` — not just static reasoning — before calling a port complete.
  Shallow route-list-only audits have missed real gaps before (`ProjectSuggestionService`); the
  corrected methodology has since found and fixed real, confirmed bugs (3MF mesh-safety guards
  only checking the root model entry, an entire missing `relocate_to_dropfolder` ingest mode,
  the periodic rescan feature being a complete no-op stub, an orphaned-empty-project cleanup
  path that was silently missing in two places).
- A fix that reproduces a real incident from the original app's `CLAUDE.md` deserves a comment
  citing it, not just a bare code change — that context is what stops someone "simplifying" the
  guard back out later.

## Design/HIG conventions established

- Prefer real macOS mechanisms over hand-rolled UI: a `Window` scene (not a `.sheet`) for the
  Admin review panel, a `Settings` scene (⌘,) for actual preferences, SwiftUI's native
  `.badge()` instead of a hand-rolled capsule, `List(selection:)` for free keyboard nav instead
  of custom hit-testing where a plain `List` is viable.
- Every icon-only control needs both `.help(...)` (tooltip) and an explicit
  `.accessibilityLabel(...)` — SF Symbol defaults are not reliably descriptive for VoiceOver.
  Never leave an interactive control as a bare `.onTapGesture` on non-Button content — it's
  invisible to VoiceOver and unreachable by keyboard.
- Reversible edits (tags, project membership, rename, relationships) are registered on
  `UndoManager` via a symmetric forward/backward re-registration pattern (see
  `FileDetailView.performAndRegisterUndo`) so redo keeps working indefinitely, not just once.
